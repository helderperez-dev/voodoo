VOODOO — RUNTIME, PROTOCOL & PROVIDER-NEUTRAL ARCHITECTURE
Architecture Direction & Implementation Guidance
Version: 2026-08-17

===============================================================================
0. PURPOSE
===============================================================================

Voodoo is evolving beyond an AI framework.

The goal is to create a runtime and protocol for software that can execute,
persist, communicate, interact with tools and the physical/digital world,
recover from failure, and host intelligent agents as first-class runtime
entities.

Long-term vision:

    "The runtime for autonomous software."

The deeper goal is to give AI systems a durable computational substrate:
memory, identity, execution, tools, communication, scheduling, storage,
permissions, observation, and the ability to act in the world.

Voodoo should make an AI agent behave less like a stateless API request and
more like a persistent software entity.

This document is implementation guidance for the AI/developers working on the
Voodoo repository.

Core rules:
- Do not rewrite working architecture without a concrete reason.
- Preserve the strongest existing Voodoo primitives.
- Prefer small, composable protocols and capability interfaces.
- Local development must remain exceptionally simple.
- Production infrastructure must be replaceable without rewriting application
  logic.
- Durability and correctness are more important than cleverness.
- Hide infrastructure complexity without hiding runtime capabilities.

===============================================================================
1. CURRENT POSITION
===============================================================================

The existing repository already contains important pieces of the target:

- Runtime / Execution Engine
- Execution objects and lifecycle
- Intent / Capability / Compute / Effect / State primitives
- Workers
- In-memory queue
- SQLite data layer
- JSONL execution persistence
- Object storage abstraction with local filesystem and S3-compatible support
- Mesh / events
- MCP
- AI/agent abstractions
- telemetry
- workflows / tasks / planning

The project should NOT be rewritten from scratch.

Immediate architectural gaps:

1. Queue is process-memory oriented and is not durable.
2. Execution persistence is split from the SQLite data layer.
3. Recovery can restore execution metadata but does not yet guarantee that an
   interrupted computation can resume from a durable checkpoint.
4. Events/Mesh and durable execution need clearer boundaries and contracts.
5. Object storage should become a first-class Voodoo capability.
6. Scheduler should become a first-class durable runtime primitive.
7. Provider adapters need formal contracts and capability discovery.
8. Production backends must be interchangeable without application coupling.
9. Voodoo Protocol must become the stable semantic boundary between application
   and infrastructure.
10. AI/agents must become first-class participants in the runtime.

===============================================================================
2. CORE ARCHITECTURAL PRINCIPLE
===============================================================================

Voodoo defines SEMANTICS.

Providers implement those semantics.

Application code depends on Voodoo contracts, not provider SDKs.

Desired dependency direction:

    Application
        |
        v
    Voodoo Protocol / SDK
        |
        v
    Voodoo Runtime
        |
        +-------------------------------+
        |                               |
        v                               v
    Capability Interfaces           Execution Engine
        |
        +----------+----------+----------+----------+
        |          |          |          |          |
        v          v          v          v          v
      SQLite    Postgres     S3/R2     Redis      SQS/etc.

The application should NOT directly depend on:
    boto3 / redis clients / psycopg / cloud SDKs / model SDKs

Instead:
    storage.put()
    tasks.dispatch()
    events.publish()
    model.generate()
    tool.call()
    execution.run()

Provider SDKs belong below the adapter boundary.

===============================================================================
3. VOODOO PROTOCOL
===============================================================================

"Voodoo Protocol" is the stable semantic contract of the Voodoo ecosystem.

It is NOT merely a network protocol.

It defines how software entities:
- execute
- persist state
- schedule work
- exchange messages
- publish events
- store objects
- invoke tools
- call models
- expose capabilities
- identify themselves
- authorize actions
- recover from failures
- report telemetry
- participate in distributed execution

The protocol must work:
- in-process
- across processes
- across machines
- through language SDKs
- through HTTP/RPC
- through MCP where appropriate

Transport is separate from semantics.

For example:

    Voodoo Task protocol
        can be implemented through:
        - local function call
        - SQLite
        - PostgreSQL
        - Redis
        - SQS
        - HTTP
        - NATS
        - Kafka

The semantic operation remains:

    dispatch(task)

===============================================================================
4. PROTOCOL LAYERS
===============================================================================

LAYER 0 — Identity
------------------

Durable/external entities need stable identities:

    application_id
    runtime_id
    agent_id
    execution_id
    task_id
    event_id
    object_id
    capability_id
    tool_id
    model_id

Never rely on process-local object identity for durable entities.

LAYER 1 — Capabilities
----------------------

Voodoo is capability-oriented.

Examples:

    storage.read
    storage.write
    network.http
    browser.control
    filesystem.read
    filesystem.write
    model.generate
    tool.invoke
    task.dispatch
    events.publish
    secrets.read

Capabilities should be declarative and inspectable.

LAYER 2 — Intent
----------------

Intent represents what an actor wants the runtime to accomplish.

It is provider-neutral.

LAYER 3 — Execution
-------------------

Execution is the durable unit of work.

An Execution should contain:

    id
    parent_id
    actor
    intent
    status
    created_at
    updated_at
    current_step
    checkpoint
    state
    capabilities
    resources
    effects
    result
    error
    trace_id

Execution must survive worker/process restarts.

LAYER 4 — Effects
-----------------

Effects represent changes to the outside world:

    HTTP request
    file write
    object upload
    database mutation
    message publish
    tool call
    browser interaction
    email send

Effects should be observable and, where possible, idempotent.

LAYER 5 — State
---------------

Durable application/runtime state is separate from:
- transient worker memory
- cache
- execution logs
- object storage

LAYER 6 — Events
----------------

Events are facts:

    document.created
    agent.started
    execution.completed
    payment.received

Events are not commands.

LAYER 7 — Tasks
---------------

Tasks represent work to be performed.

Queue semantics belong here.

LAYER 8 — Objects
-----------------

Objects represent large/blob data:

    files
    images
    videos
    datasets
    model artifacts
    generated documents

LAYER 9 — Intelligence
----------------------

Models, agents, memory and tools become runtime capabilities.

6. LOCAL RUNTIME — "WAMP FOR AUTONOMOUS SOFTWARE"
===============================================================================

WAMP is a useful analogy: one installation provided a complete local web
development environment.

Voodoo should provide the equivalent experience for AI-native software.

Desired experience:

    voodoo create my-app
    cd my-app
    voodoo dev

The developer gets:

    runtime
    server/API
    SQLite
    durable task queue
    workers
    scheduler
    event bus
    object storage
    local cache
    secrets/configuration
    telemetry
    agent runtime
    MCP/tool runtime

No Redis.
No Postgres.
No Docker.
No S3.
No Kafka.
No external queue.

Local defaults:

    database      -> SQLite
    queue         -> SQLite
    execution     -> SQLite
    event log     -> SQLite
    scheduler     -> SQLite
    object store  -> local filesystem
    cache         -> process memory / SQLite as appropriate
    workers       -> local processes/tasks
    messaging     -> local runtime bus
    telemetry     -> local structured logs

This is a core product feature.

===============================================================================
7. PRODUCTION RUNTIME
===============================================================================

Production preserves the same application semantics.

A deployment may become:

    database      -> PostgreSQL
    queue         -> PostgreSQL initially
    event bus     -> PostgreSQL / NATS / Redis Streams / Kafka
    object store  -> S3 / R2 / GCS / Azure Blob
    cache         -> Redis
    scheduler     -> PostgreSQL / distributed scheduler
    workers       -> containers / VMs / Kubernetes / serverless
    secrets       -> provider secret manager
    telemetry     -> OpenTelemetry backend

The application should not need to know.

Moderate production should be possible with:

    PostgreSQL + S3/R2

and no Redis/SQS.

At larger scale:

    PostgreSQL + S3/R2 + Redis + NATS/Kafka/SQS

without changing agent/application code.

Each capability has a stable Voodoo interface and provider implementations.

Object store:

    VoodooObjectStore
        +-- LocalObjectStore
        +-- S3ObjectStore
        +-- R2ObjectStore
        +-- GCSObjectStore
        +-- AzureBlobObjectStore

Queue:

    VoodooQueue
        +-- SQLiteQueue
        +-- PostgresQueue
        +-- RedisQueue
        +-- SQSQueue

Events:

    VoodooEventBus
        +-- LocalEventBus
        +-- SQLiteEventBus
        +-- PostgresEventBus
        +-- RedisEventBus
        +-- NATSBus
        +-- KafkaBus

Database:

    VoodooDatabase
        +-- SQLite
        +-- PostgreSQL

Models:

    VoodooModelProvider
        +-- OpenAI
        +-- Anthropic
        +-- Gemini
        +-- OpenRouter
        +-- Ollama
        +-- custom provider

Provider SDKs must never leak into the semantic API.

===============================================================================
9. ADAPTER CONTRACTS
===============================================================================

Every adapter should declare:

    provider
    capabilities
    limits
    consistency model
    durability model
    transaction support
    idempotency behavior
    retry behavior
    ordering guarantees
    delivery guarantees
    latency characteristics
    configuration requirements

Example queue declaration:

    delivery: at_least_once
    ordering: best_effort
    visibility_timeout: supported
    delayed_delivery: supported
    transactions: supported

Do not pretend all providers are equivalent.

Provider abstraction means:
    common semantics + explicit capability differences

not:
    erase all provider differences.

===============================================================================
10. CAPABILITY NEGOTIATION
===============================================================================

Adapters should support capability discovery.

Example:

    provider.capabilities()

Possible result:

    queue:
      durable: true
      delayed: true
      priority: true
      visibility_timeout: true
      ordering: false

The runtime may:
- emulate a feature when safe
- reject an unsupported required operation
- degrade explicitly

Never silently violate correctness.

===============================================================================
11. DATABASE STRATEGY
===============================================================================

SQLite is the default embedded database.

PostgreSQL is the primary production relational backend.

Do not create a proprietary database.

SQLite should support:

    state
    executions
    tasks
    leases
    events
    schedules
    metadata
    memory metadata

PostgreSQL should support the same logical model.

Do not expose SQLite-specific APIs as the public programming model.

===============================================================================
12. DURABLE QUEUE
===============================================================================

Queue must be durable from the beginning.

Local implementation:
    SQLite

Conceptual task:

    id
    type
    payload
    status
    priority
    available_at
    attempts
    max_attempts
    locked_by
    locked_at
    lease_until
    created_at
    completed_at
    last_error
    idempotency_key

Lifecycle:

    PENDING
      |
      v
    CLAIMED
      |
      v
    RUNNING
      |
      +------> COMPLETED
      |
      +------> RETRYING
      |
      +------> FAILED

If a worker disappears:

    RUNNING
       |
       v
    lease expires
       |
       v
    PENDING / RETRYING

Queue must not depend on worker memory.

Use transactional claiming.

PostgreSQL can use SKIP LOCKED where appropriate.
SQLite needs carefully designed atomic claim/lease semantics.

===============================================================================
13. DURABLE EXECUTION
===============================================================================

Execution durability is more important than worker durability.

Worker is disposable.

Execution is persistent.

Persist enough information to recover:

    execution metadata
    current state
    current step
    checkpoint
    pending tasks
    event sequence
    outputs/references
    retry state

Prefer an append-oriented execution event journal plus materialized state.

Conceptual table:

    execution_events

    sequence
    execution_id
    event_type
    payload
    timestamp

Examples:

    execution.created
    execution.started
    step.started
    model.called
    model.completed
    tool.called
    tool.completed
    state.changed
    task.scheduled
    execution.waiting
    execution.completed

===============================================================================
14. CHECKPOINTING
===============================================================================

A durable execution must know where it can safely resume.

Checkpoint at meaningful boundaries:

    after model completion
    after tool completion
    after state mutation
    before waiting
    after task scheduling

Do not assume arbitrary Python process memory is recoverable.

Prefer durable representations:

    JSON-compatible state
    typed records
    object-store references
    stable execution inputs
    deterministic identifiers

Avoid serializing arbitrary live Python objects.

===============================================================================
15. IDEMPOTENCY
===============================================================================

At-least-once execution means work may run more than once.

Therefore Voodoo must embrace idempotency.

Effects should support:

    idempotency_key

Examples:

    payment.charge:<execution_id>
    email.send:<message_id>
    object.put:<object_id>
    webhook.call:<operation_id>

Never promise exactly-once external effects unless the external system really
provides the necessary semantics.

===============================================================================
16. EVENTS VS QUEUES VS MESSAGING
===============================================================================

Keep these concepts distinct.

EVENT:
    A fact that happened.

TASK / QUEUE:
    Work that should happen.

COMMAND:
    A request to perform an operation.

MESSAGE:
    A transport envelope carrying a command/event/etc.

Example:

    command:
        generate_report

    task:
        report_generation

    event:
        report.generated

Queue distributes work.
Event bus distributes facts.
Messaging transports structured messages.

===============================================================================
17. VOODOO MESH
===============================================================================

The existing Mesh/event system should evolve into the runtime's event/messaging
layer.

Support:
- local events
- cross-process events
- future distributed events
- MCP integration
- WebSocket/realtime integration
- subscriptions
- correlation IDs
- causation IDs

Event envelope should preferably contain:

    event_id
    event_type
    timestamp
    source
    subject
    correlation_id
    causation_id
    payload
    schema_version

Mesh must not depend on one transport.

===============================================================================
18. OBJECT STORAGE
===============================================================================

Object storage is a first-class primitive.

API:

    put
    get
    delete
    exists
    stat
    list
    presign / url where supported

Local:

    .voodoo/objects/

Production:

    S3
    Cloudflare R2
    GCS
    Azure Blob

Large binary data should not normally live inside SQLite/Postgres.

Store references containing:

    object_id
    bucket
    key
    size
    content_type
    checksum
    metadata

===============================================================================
19. MEMORY
===============================================================================

AI memory must not be equated with a vector database.

Layers:

    working memory
    execution memory
    durable application memory
    semantic memory
    episodic memory
    external knowledge

The protocol should define memory semantics.

Backends can later include:

    SQLite/Postgres
    pgvector
    external vector databases
    object storage
    specialized memory providers

Agents use:

    memory.search()
    memory.read()
    memory.write()

not a specific vector database.

20. MODEL PROVIDER ABSTRACTION
===============================================================================

Models are providers, not application architecture.

Expose a normalized interface while preserving provider capabilities.

Core concepts:

    model.generate()
    model.stream()
    model.embed()
    model.count_tokens() where available

Model descriptors should expose:

    provider
    model
    modalities
    context_window
    tool_use
    structured_output
    streaming
    reasoning
    vision
    audio
    embeddings
    limits
    pricing metadata where available

Support routing aliases:

    best
    fast
    cheap
    vision
    reasoning

The runtime resolves aliases.

===============================================================================
21. AI AGENTS AS RUNTIME ENTITIES
===============================================================================

Agent is a durable runtime entity.

Agent should have:

    identity
    capabilities
    memory
    model policy
    tools
    execution history
    state
    permissions
    configuration

An Agent run creates an Execution.

Therefore:

    Agent
       |
       v
    Execution
       |
       +-- model calls
       +-- tool calls
       +-- tasks
       +-- events
       +-- state
       +-- memory
       +-- effects

Agents do not own separate queue/persistence systems.

===============================================================================
22. TOOLS AND MCP
===============================================================================

Tools are capabilities exposed to an execution.

MCP is one transport/protocol for discovering and invoking tools, not the
entire Voodoo tool model.

Conceptual:

    Voodoo Tool
       +-- local function
       +-- HTTP API
       +-- MCP tool
       +-- browser
       +-- shell
       +-- database
       +-- external service

Tool execution should produce:
- execution/effect record
- input metadata
- output/reference
- duration
- error
- telemetry
- permission context

===============================================================================
23. SECURITY AND AUTHORIZATION
===============================================================================

Security is capability-oriented.

Every meaningful external effect should have authorization context:

    actor
    principal
    capability
    resource
    scope
    policy
    approval

Sensitive capabilities:

    filesystem.write
    network.request
    shell.execute
    secrets.read
    payment.execute
    email.send

should be explicit.

Agents should not receive ambient authority by default.

===============================================================================
24. SECRETS
===============================================================================

Expose a Voodoo secret interface:

    secrets.get("OPENAI_API_KEY")

Local:
    environment variables / encrypted local store

Production:
    AWS Secrets Manager
    GCP Secret Manager
    Azure Key Vault
    Vault
    platform secret stores

Never persist plaintext secrets into execution events.

===============================================================================
25. SCHEDULING
===============================================================================

Scheduler is a durable runtime primitive.

Support:

    schedule.at()
    schedule.after()
    schedule.every()
    cron-like schedules where useful

Schedules create durable tasks.

They survive process/machine restarts.

Do not implement scheduling only as a non-persistent Python loop.

===============================================================================
26. WORKERS
===============================================================================

Workers are disposable execution capacity.

Workers should:
- claim durable tasks
- acquire leases
- execute
- heartbeat where appropriate
- checkpoint
- acknowledge completion
- release/recover leases
- report telemetry

Workers are never the source of truth.

Source of truth is durable runtime state.

Observe:

    model call
    tool call
    event
    database operation

Useful CLI:

    voodoo status

    voodoo tasks

    voodoo events

    voodoo doctor

        PostgreSQL

Every adapter should pass a common contract test suite.

Examples:

    QueueContractTests
    ObjectStoreContractTests
    EventBusContractTests

30. FAILURE SEMANTICS
===============================================================================

Every capability must define:

- retryability
- idempotency
- durability
- transactionality
- timeout behavior
- cancellation
- lease behavior
- ordering guarantees
- delivery guarantees
- resumability

Never hide these semantics.

Conceptual:

    voodoo.yaml

    database:
      provider: postgres

32. LANGUAGE SDKs
===============================================================================

Voodoo Protocol must be language-neutral.

Canonical semantics can start in Python, but the protocol must not be
Python-specific.

Future SDKs:

    Python
    TypeScript
    Go
    Rust
    others as justified

Common concepts:

    Execution
    Intent
    Task
    Event
    Capability
    Tool
    Agent
    Storage
    Object
    Model
    Memory

Do not independently reimplement business semantics in every SDK.

===============================================================================
33. PROTOCOL VERSIONING
===============================================================================

Protocol entities must be versioned.

Events include schema/version information.

Example:

    execution.completed.v1

or:

    schema_version: 1

Persisted data must not depend on today's Python class layout.

Use migrations.

Protocol compatibility must be intentional.

===============================================================================
34. DISTRIBUTED FUTURE
===============================================================================

Do not build distributed infrastructure prematurely.

But ensure contracts allow:

    Machine A -> API
    Machine B -> Workers
    Machine C -> Workers
    PostgreSQL
    S3/R2
    Event Bus

The application sees:

    Voodoo Runtime

not:

    many infrastructure services.

At large scale, specialized providers can replace individual backends.

===============================================================================
35. NO INFRASTRUCTURE REQUIRED
===============================================================================

A developer should build a serious Voodoo application without installing
infrastructure services.

The first experience:

    install Voodoo
    write code
    run Voodoo
    application works

Infrastructure appears only when scale requires it.

===============================================================================
36. ESCAPE HATCH
===============================================================================

Voodoo is opinionated by default but never a prison.

Every capability has an adapter boundary.

Advanced users can choose:

    Postgres
    Redis
    SQS
    NATS
    Kafka
    S3
    R2
    GCS
    Azure
    external model providers
    custom providers

The default remains Voodoo-native.

===============================================================================
37. WHAT NOT TO DO
===============================================================================

DO NOT:

1. Make Redis mandatory.
2. Make Postgres mandatory for local development.
3. Make S3 mandatory.
4. Create multiple competing execution engines.
5. Give each Agent its own queue.
6. Store durable state only in worker memory.
7. Treat asyncio.Queue as durable infrastructure.
8. Couple the public API to provider SDKs.
9. Treat MCP as the entire Voodoo protocol.
10. Treat vector databases as the definition of memory.
11. Promise exactly-once effects without real guarantees.
12. Serialize arbitrary Python runtime objects as the persistence format.
13. Add distributed infrastructure before the local runtime is correct.
14. Replace existing good primitives without a concrete reason.
15. Create provider-specific APIs in application code.
16. Erase meaningful provider semantics behind overly generic abstractions.

40. IMPLEMENTATION ORDER
===============================================================================

PHASE 0 — ARCHITECTURE SAFETY
-----------------------------
- map existing modules
- identify public APIs
- identify tests
- preserve backward compatibility where practical
- document current semantics
- add contract tests

PHASE 1 — UNIFIED STORAGE CORE
------------------------------
Create internal storage interfaces.

Implement:
- SQLite database
- ExecutionStore
- TaskStore
- EventStore
- StateStore

Make SQLite the local source of truth.

PHASE 2 — DURABLE QUEUE
-----------------------
Replace in-memory-only queue as the source of truth.

Implement:
- task persistence
- atomic claim
- leases
- retries
- attempts
- timeout
- idempotency
- recovery

Workers become consumers of durable tasks.

PHASE 3 — DURABLE EXECUTION
----------------------------
Implement:
- execution journal
- checkpoints
- durable state
- resume/recovery
- pending work reconstruction

PHASE 4 — FIRST-CLASS OBJECT STORE
-----------------------------------
Formalize:
- ObjectStore interface
- local implementation
- S3-compatible implementation
- metadata/checksum
- object references

PHASE 5 — EVENTS/MESSAGING
---------------------------
Formalize:
- Event
- EventBus
- subscriptions
- correlation/causation
- durable event storage where required

Unify with Mesh where appropriate.

PHASE 6 — SCHEDULER
-------------------
Implement durable schedules.

PHASE 7 — PROVIDER ADAPTERS
----------------------------

===============================================================================
41. AI-NATIVE WORLD MODEL
===============================================================================

The purpose of these abstractions is not infrastructure elegance.

It is to make intelligent software capable of acting over time.

Traditional application:

    request -> function -> response

Voodoo application:

    intent
      ->
    execution
      ->
    reason
      ->
    tool
      ->
    external world
      ->
    observation
      ->
    state
      ->
    event
      ->
    next action
      ->
    execution continues

The system must survive between actions.

An AI should be able to:
- remember
- observe
- decide
- act
- wait
- receive events
- schedule future work
- recover after failure
- interact with tools
- create artifacts
- communicate with other agents
- ask for human approval
- continue execution later

This requires a runtime, not an LLM wrapper.

===============================================================================
42. AGENT "LIFE"
===============================================================================

Treat "life" as a runtime abstraction, not a claim about consciousness.

An agent has:

    identity
    state
    memory
    capabilities
    environment
    execution history
    goals/intents
    tools
    observations
    actions
    schedules
    relationships

Conceptually:

    Agent
      |
      +-- perceives through events/tools
      |
      +-- reasons through models
      |
      +-- acts through effects
      |
      +-- remembers through state/memory
      |
      +-- waits through durable execution
      |
      +-- wakes through events/schedules
      |
      +-- survives through persistence

This is the software foundation for persistent AI agents.

===============================================================================
43. MULTI-AGENT SYSTEMS
===============================================================================

Agents communicate through Voodoo primitives.

Do not create bespoke agent-to-agent RPC for every feature.

Example:

    Agent A
      |
      | event/command/task
      v
    Voodoo Runtime
      |
      v
    Agent B

Each agent remains independently observable and durable.

Parent/child executions should preserve tracing relationships.

===============================================================================
44. HUMAN-IN-THE-LOOP
===============================================================================

Human approval is a runtime capability.

An execution may enter:

    WAITING_FOR_HUMAN

The process may terminate.

Later:

    human approves
       ->
    event/command
       ->
    execution resumes

Do not require the original worker process to remain alive.

===============================================================================
45. EXTERNAL WORLD
===============================================================================

The runtime's most important boundary is the outside world.

External effects include:
- web requests
- browser automation
- filesystem
- devices
- APIs
- databases
- payments
- messaging
- email
- code execution
- IoT
- future robotics

All interaction should be represented through capabilities/effects/tools.

The runtime should know:
- what was attempted
- who attempted it
- what capability was used
- what resource was affected
- whether it succeeded
- whether it can be retried
- what evidence/result was produced

===============================================================================
46. ARTIFACTS AND PROVENANCE
===============================================================================

AI-generated outputs should be durable artifacts.

Examples:

    generated report
    image
    dataset
    code patch
    browser snapshot
    model output
    tool result

Use object storage for large data.

Record provenance:

    artifact_id
    execution_id
    parent_artifact_id
    created_by
    tool/model
    timestamp
    checksum
    metadata

This creates a durable history of what the AI produced and why.

===============================================================================
47. REPRODUCIBILITY
===============================================================================

AI execution is inherently non-deterministic.

Voodoo should maximize reproducibility through:
- recorded inputs
- model/provider metadata
- tool inputs
- tool outputs/references
- prompt/configuration references
- random seeds where supported
- execution events
- versions
- checkpoints

Do not promise deterministic AI behavior.

Provide an auditable execution history.

===============================================================================
48. DATA MODEL PRINCIPLES
===============================================================================

Use durable identifiers.

Prefer explicit schemas.

Prefer JSON-compatible payloads at protocol boundaries.

Avoid leaking Python class serialization into persisted protocol state.

Separate:
- metadata
- payload
- state
- events
- objects

Large payloads should be object references.

Version schemas.

Use migrations.

===============================================================================
49. PERFORMANCE PRINCIPLES
===============================================================================

Optimize after correctness.

Local SQLite should be surprisingly capable.

Use:
- WAL where appropriate
- indexes
- transactional writes
- batched operations
- connection pooling where relevant
- bounded concurrency

PostgreSQL is the scaling path.

Redis/Kafka/SQS are specialized scaling paths.

Do not prematurely distribute everything.

===============================================================================
50. TESTING STRATEGY
===============================================================================

Tests must include failure.

Not only:

    task completes

but:

    worker crashes
    process restarts
    machine restarts
    lease expires
    duplicate delivery
    provider timeout
    network failure
    model failure
    tool failure
    database transaction failure
    object upload failure
    event delivery failure

Critical invariants:

    A durable execution must never silently disappear.

    A task must never become permanently invisible because a worker died.

    External effects must not be retried blindly when non-idempotent.

51. ARCHITECTURAL INVARIANTS
===============================================================================

1. Workers are disposable.
2. Executions are durable.
3. Queues are durable.
4. Events have explicit semantics.
5. Effects are observable.
6. Provider SDKs do not leak into application code.
7. Local development requires no external infrastructure.
8. Production providers are replaceable.
9. SQLite is a first-class local backend.
10. PostgreSQL is a first-class production backend.
11. Object storage is a first-class capability.
12. AI agents use the common runtime.
13. MCP is a tool integration, not the entire runtime.
14. Memory is a capability, not a specific vector database.
15. Protocol schemas are versioned.
16. Failures are explicit.
17. Idempotency is designed, not assumed.
18. Security is capability-based.
19. Observability is execution-aware.
20. Distributed infrastructure is optional, not foundational.

===============================================================================
52. DEFINITION OF DONE — DURABLE RUNTIME
===============================================================================

The first major runtime milestone is complete when:

1. An execution can start.
2. Its state is persisted in SQLite.
3. It can enqueue durable tasks.
4. A worker can claim a task.
5. The worker can crash.
6. The lease expires.
7. Another worker can claim the task.
8. Execution state remains intact.
9. Runtime can recover after process restart.
10. Checkpoints identify safe resume points.
11. Events describe execution history.
12. Object artifacts can be stored locally.
13. The same semantic APIs can use PostgreSQL/S3 later.
14. No Redis/SQS/Postgres installation is required locally.
15. Tests verify failure paths.

54. FINAL GUIDANCE TO THE IMPLEMENTING AI
===============================================================================

When modifying Voodoo, think in systems, not isolated features.

Before adding a feature ask:

    What is the semantic primitive?

    Is it:
        state?
        execution?
        task?
        event?
        object?
        capability?
        effect?
        identity?
        memory?
        tool?

Then ask:

    Should this survive restart?

If yes:
    persist it.

Then ask:

    Is this infrastructure-specific?

If yes:
    create an adapter.

Then ask:

    Can the local runtime implement this without external services?

If yes:
    make that the default.

Then ask:

    What happens when the worker dies?

If the answer is "the state is lost":
    the architecture is not finished.

Then ask:

    Can the provider be replaced without changing application code?

If no:
    the boundary is in the wrong place.

Then ask:

    Can an AI agent observe, decide, act, wait, wake up, remember, recover,
    and continue?

If no:
    the runtime is not yet fulfilling its purpose.

Do not optimize for the maximum number of integrations.

Optimize for a small number of extremely strong primitives.

Voodoo should feel simple at the surface and deeply capable underneath.

The developer should see:

    voodoo agent
    voodoo task
    voodoo event
    voodoo storage
    voodoo memory
    voodoo tool
    voodoo execution

while the runtime handles:

    persistence
    queues
    workers
    recovery
    scheduling
    providers
    security
    telemetry
    distributed execution

The ultimate architectural principle is:

    BUILD THE SEMANTICS ONCE.
    SWAP THE INFRASTRUCTURE UNDERNEATH.

The ultimate product principle is:

    MAKE AUTONOMOUS SOFTWARE AS EASY TO START AS A LOCAL WEB APP,
    BUT AS CAPABLE AS A DISTRIBUTED CLOUD RUNTIME.

Voodoo should not force developers to assemble the infrastructure required for
intelligent software.

Voodoo should BE that substrate.
